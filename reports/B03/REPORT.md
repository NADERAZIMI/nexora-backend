## 1. Roadmap steps and scope

The ten B03 steps were implemented:

1. PostgreSQL 17 identity schema and reversible migrations.
2. Registration with email/phone verification and Argon2id password hashing.
3. Login with Ed25519 JWTs and rotating refresh tokens with reuse detection.
4. TOTP and WebAuthn second factors.
5. API keys with scopes, IP allowlists, expiry, revocation, constant-time
   verification, and one-time secret reveal.
6. RBAC with customer/admin separation and deny-by-default authorization.
7. Rate limiting, account lockout, and exponential backoff.
8. Append-only, hash-chained audit events.
9. Adversarial security tests for enumeration, replay, IDOR, scope escalation,
   token reuse, and cross-account access.
10. Session and API-key revocation effective on the next authenticated request,
    well inside the 60-second propagation requirement.

No frontend files were changed. There is no frontend directory in this
repository, and the changed-file set is backend/contract/tooling only.

### 1.1 Explicit non-goals

- No B04 reference-data implementation.
- No ledger, matching engine, wallet, futures, custody, or withdrawal logic.
- No live email/SMS provider, payment provider, KYC provider, or production
  third-party account.
- No claim that a simulated authentication success is a real ceremony. WebAuthn
  success paths and live delivery are marked BLOCKED where not executed.

## 3. Schema and migrations

`services/identity-service/migrations/0001_identity.up.sql` creates the
`identity` schema and 15 tables:

`users`, `credentials`, `sessions`, `refresh_tokens`, `api_keys`,
`user_roles`, `verification_tokens`, `mfa_challenges`, `webauthn_challenges`,
`login_attempts`, `audit_events`, `audit_heads`, `api_key_nonces`,
`kyc_cases`, and `notification_outbox`.

Key properties:

- UUID primary keys; UUIDv7 generated by the service.
- Unique normalized email/phone hashes and unique API-key prefix.
- `CHECK` constraints for statuses, outcomes, scopes, nonce length, KYC level,
  and refresh-token states.
- Foreign keys and cascade behavior for user-owned child records.
- Partial indexes for live sessions, live API keys, pending outbox rows, and
  pending audit reads.
- `audit_events` is protected by a trigger that rejects `UPDATE` and `DELETE`.
- `audit_heads` stores the latest hash chain head.
- `api_key_nonces` has a `(key_id, nonce)` primary key for replay rejection.
- The down migration removes the identity schema completely.
- The migration runner applies embedded/reversible migrations in order and was
  executed both up and down against PostgreSQL 17.

Production migrations are not implicitly run. `NEXORA_IDENTITY_AUTO_MIGRATE`
defaults to true only for development/test and must be enabled explicitly
elsewhere; production configuration requires external key material.

## 4. Security design decisions

### 4.1 Passwords and enumeration

- Argon2id defaults: 64 MiB, 3 iterations, 4 lanes, 16-byte salt, 32-byte key.
- A server-side pepper is applied with HMAC-SHA-256 before Argon2id.
- Password policy rejects short, common, repeated, and trivially patterned
  passwords.
- Unknown accounts execute a dummy Argon2id verification to reduce timing
  enumeration.
- Registration and password-reset request responses are deliberately uniform.
- Password hashes, refresh tokens, API secrets, verification tokens, TOTP
  secrets, and recovery codes are never stored in plaintext.

### 4.2 JWT and sessions

- Access tokens are Ed25519-signed JWTs.
- Issuer, audience, signing algorithm, token type, expiry, and signature are
  validated explicitly.
- The injected clock is shared by issuance and validation.
- Session state is read from PostgreSQL on every authenticated request; a
  revoked or expired session fails immediately.
- Access TTL defaults to 15 minutes. Refresh TTL defaults to 30 days.
- Refresh rotation is atomic. The old token is marked used, a new token is
  stored, and the session is checked under the same transaction.
- Reuse of a rotated refresh token revokes the session family and returns a
  generic authentication failure.
- Logout revokes the session, live refreshes, and API keys in one transaction.
- Password reset revokes all sessions and API keys before the new password can
  be used.

### 4.3 MFA and step-up

- TOTP follows RFC 6238 with a bounded validation window and replay-step
  tracking.
- TOTP enrollment is confirmed in a single transaction with MFA enrollment and
  audit writes.
- Recovery codes are one-time, generated with at least 256 bits of entropy,
  normalized before hashing, and stored only as SHA-256 digests.
- WebAuthn validates relying-party ID, allowed origins, server-side challenge,
  challenge expiry, and the library-verified assertion signature.
- WebAuthn registration consumes the challenge, inserts the credential, enables
  MFA, and writes audits in one transaction.
- WebAuthn assertion consumption and authenticator signature-counter update are
  one transaction, preventing challenge replay and counter-update races.
- API-key creation/revocation, recovery-code generation, and privileged admin
  mutations require an action-bound, short-lived step-up token.
- Wrong TOTP/recovery/WebAuthn second factors feed the same account backoff and
  lockout state as wrong passwords.

### 4.4 API keys

- Two verification modes: HMAC-SHA-256 shared secret and Ed25519 signatures.
- Only a one-time plaintext secret is returned on creation; storage is
  encrypted and verification uses constant-time comparison or Ed25519 verify.
- Scopes are validated against a closed allowlist and cannot be escalated by
  clients.
- IP allowlists are parsed as CIDR/address prefixes and all-zero Ed25519 public
  keys are rejected.
- Expiry and revocation are enforced on every request.
- Signed requests include method, path, timestamp, nonce, and body hash.
- Nonces are consumed with a database uniqueness constraint, giving a single
  winner under concurrency.
- API-key prefixes use independent random bytes to avoid UUIDv7 prefix
  collisions.

### 4.5 Authorization

- Permissions are explicit server-side constants.
- Unknown roles and permissions grant nothing.
- Customer roles never receive `admin:*`; administrative roles do not receive
  customer-only `api_key:manage`.
- Roles are loaded from PostgreSQL on each request, so role removal is effective
  immediately.
- Admin routes require a session principal, the exact permission, and step-up
  where the action is privileged.
- Resource ownership is checked before session, API-key, KYC, or audit access.
- Cross-account object identifiers return the same not-found/denied response
  shape used for missing objects.

### 4.6 Abuse controls

- Per-IP HTTP token-bucket limiting with bounded cardinality (hard cap plus
  stale-entry eviction).
- Password login failures are counted by keyed subject hash and IP hash.
- Exponential backoff begins after repeated failures; lockout follows the
  configured threshold and is capped.
- MFA failures and step-up failures feed the same counters.
- Successful completion clears the subject counter but retains the zero-subject
  IP bucket to preserve credential-stuffing protection.
- `Retry-After` and `retryAfterSeconds` are returned for limited/locked responses.

### 4.7 Audit, privacy, and secrets

- Audit events use a SHA-256 hash chain (`prev_hash`, `event_hash`) and a
  serialized head update.
- Audit writes for successful security mutations occur in the same transaction
  as the mutation.
- Denied security events are recorded without credentials or token material.
- Email/phone values are encrypted with AES-256-GCM; lookups use keyed hashes.
- IP addresses and user agents are hashed or truncated before storage.
- Notification destinations and payloads are encrypted in the outbox.
- Logs, metrics, traces, and error responses avoid passwords, refresh tokens,
  secrets, and raw bearer credentials.
- JSON bodies are limited to 1 MiB, unknown fields are rejected, and trailing
  JSON is rejected.
- Security headers include `nosniff`, `DENY`, `no-referrer`, `no-store`, and a
  restrictive CSP.

### 4.8 Fail-closed configuration

Production configuration requires:

- An explicit database URL.
- Non-ephemeral 32-byte secrets for password, PII, IP, PII-encryption, and
  secret-encryption domains.
- An external Ed25519 JWT private-key file.
- gRPC TLS certificate/key and a client CA for mTLS.
- Non-development WebAuthn RP ID/origins.

Missing or invalid material aborts startup. Ephemeral keys are accepted only in
development/test. Private keys are excluded from source control.

### 4.9 Transaction boundaries

Atomic operations include:

- User creation with password credential, verification token, roles, and audit.
- Session creation with refresh token, active-session limit enforcement, and
  audit.
- Refresh rotation and reuse revocation.
- TOTP confirmation and MFA enrollment.
- Contact verification and user activation.
- Password reset, password replacement, and full session/API-key revocation.
- WebAuthn registration and assertion/counter updates.
- API-key creation/revocation and nonce consumption.
- Admin freeze/unfreeze with session and API-key revocation.
- Audit append and hash-head update.

### 4.10 Revocation propagation

Sessions, users, roles, and API keys are authoritative in PostgreSQL and checked
on every request. Revocation therefore applies to the next authenticated request,
not after a background delay. Executable tests confirm that a bearer token fails
immediately after logout, password reset, refresh-reuse detection, and admin
freeze. This is below the 60-second B03 requirement.

## 10. Blockers, risks, and carry-forward items

### 10.1 B03 blockers

1. **WebAuthn positive ceremony:** validation, negative paths, and transactional
   store operations were executed, but a full browser/software-authenticator
   registration and assertion were not. Do not claim end-to-end WebAuthn.
2. **Live recovery/verification delivery:** tokens are queued to an encrypted
   outbox and captured in tests. No email/SMS provider is configured, so real
   delivery is unverified.
3. **Production KMS:** keys are loaded from base64 environment material or an
   external PEM file. No cloud KMS/HSM envelope integration exists.
4. **Docker/Compose runtime:** static files are present, but image builds and
   `docker compose config` were not executed locally.

### 10.2 Design and verification risks

- Local govulncheck retries received HTTP 403 from `vuln.go.dev`. CI run 4
  executed govulncheck successfully for libs, hello-service, and
  identity-service.
- cargo/rustc are absent locally. CI run 4 passed the Rust,
  financial-verification, and cargo-deny jobs after the `rustls-webpki` bump.
- Per-request PostgreSQL checks give immediate revocation but add database load.
  Connection pooling and indexes are configured; horizontal scaling still needs
  production load evidence.
- The in-process IP limiter is per instance. A multi-instance deployment needs a
  shared edge limiter or gateway policy.
- Refresh lifetime defaults to 30 days. Rotation and reuse detection are in
  place, but a shorter production value should be reviewed against product
  requirements.
- Prometheus and OTLP endpoints are wired, but actual collector delivery was not
  observed in this phase.

### 10.3 B02 carry-forward limitations

These remain from the accepted B02 baseline and were not expanded in B03:

- OTLP delivery was not observed.
- Ten npm advisories remain below the critical CI threshold.
- Fuzz campaigns are limited to corpus regression.
- The conversion benchmark margin is narrower than ideal.
- GNU Make is not installed locally; the PowerShell/Go equivalents were run.
