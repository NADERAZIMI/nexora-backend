### Security correction: cloned-authenticator counter regression

`go-webauthn` does not reject a non-increasing assertion signature counter. It
sets `Credential.Authenticator.CloneWarning`. Before this phase the identity
service ignored that flag. `FinishWebAuthnLogin` now:

1. rejects the assertion with HTTP 401 and `AUTH_WEBAUTHN_FAILED`;
2. writes an `auth.webauthn.clone_warning` denied audit event;
3. leaves the stored signature counter unchanged;
4. does not consume the challenge, so a legitimate user can retry.

The behavior is covered by
`TestWebAuthnRejectsClonedAuthenticatorCounter`, including the audit outcome and
the unchanged counter.

## D. WebAuthn verification

### Authenticator implementation

The software authenticator performs real cryptography and does not share code
with the relying-party verifier:

- P-256 key pair generated with `crypto/ecdsa`;
- credential ID: 32 random bytes;
- `clientDataJSON` type `webauthn.create` / `webauthn.get`, real challenge,
  origin, and `crossOrigin:false`;
- authenticator data: SHA-256 RP ID hash, UP|UV|AT flags (`0x45`) for
  registration and UP|UV flags (`0x05`) for assertions, big-endian signature
  counter;
- COSE EC2 public key with `kty=2`, `alg=-7` (ES256), `crv=1` (P-256);
- CBOR attestation object with `fmt:"none"` and empty `attStmt`;
- assertion signature: ES256 over
  `authenticatorData || SHA-256(clientDataJSON)`, with the required SHA-256
  digest before `ecdsa.SignASN1`.

Test relying-party settings: RP ID `localhost`, origin
`http://localhost:8082`.

## E. Authentication integration

### JWT / JWKS contract

The identity service validates Ed25519/EdDSA access tokens and enforces:

- EdDSA as the only accepted algorithm (including rejection of `alg:none` and
  symmetric algorithms);
- trusted key identifier;
- issuer;
- audience;
- expiry and not-before/issued-at validity;
- access-token type;
- malformed and tampered-token rejection.

New `TestPublishedJWKSVerifiesAccessTokenForDownstreamServices` PASS:

- reads the published JWKS and asserts `kty=OKP`, `crv=Ed25519`, `use=sig`,
  `alg=EdDSA`, and the absence of private key material (`d`);
- reconstructs the Ed25519 public key from the JWK `x` coordinate;
- independently parses and verifies an issued access token with only that
  public key plus issuer, audience, expiry, and `kid` policy;
- verifies subject, session ID, type, and MFA claims;
- rejects the same token with a different public key.

This demonstrates that the published JWKS is consumable by a future Go or Rust
service without relying on identity-service internals.

### Authoritative authorization

New `TestJWTClaimsAreNotAuthoritative` PASS:

- a token minted with an `admin` role claim for a live customer session resolves
  to the customer role and gains no administrator permission;
- after the authoritative store changes the user to `support`, the same
  already-issued token resolves to `support` and loses the customer role.

This proves authorization comes from PostgreSQL-backed state, not JWT claims.
Existing gRPC tests also exercise `GetPermissions` returning the authoritative
permission set.

### Revocation

The identity service rejects revoked state on the next request. Existing B03
tests cover logout, explicit session revocation, API-key revocation, and
password-reset revocation of sessions and API keys. B03-FIX01 adds WebAuthn
credential revocation and PostgreSQL-backed assertion coverage.

Because the identity service performs no authorization caching, session,
role, and credential revocation are immediate for requests it serves. The
60-second bound remains the architectural maximum for any future downstream
decision cache; no such cache is deployed in B03.

### Go and Rust readiness

There are no downstream Go or Rust authentication clients in the repository
yet. `libs/go` contains configuration, HTTP, logging, observability, and version
helpers only. No Rust service consumes JWTs or JWKS.

Consequently the integration status is **contract-ready, not client-complete**:

- the OpenAPI document publishes the Ed25519 JWKS and OpenID metadata;
- the gRPC contract exposes `GetPermissions(access_token)` for authoritative
  permission decisions;
- the architecture document now states that JWKS caching is permitted for
  signature verification only, that JWT role/scope claims are not authoritative
  for sensitive operations, and that authoritative checks must fail closed;
- no new identity system, duplicate role store, or unapproved service was
  introduced.

These are environment-specific smoke measurements, not production capacity
claims. The path performs JWT verification and **three sequential PostgreSQL
round trips**: session lookup, user lookup, and role lookup. `postgres.New`
keeps the pgx pool default (the greater of 4 or `runtime.NumCPU()`) when it is
within 4–32 connections and otherwise clamps it to 12; it sets minimum 1
connection, a 30-minute maximum lifetime, and a 5-minute idle time. Under
concurrency each query checks out and returns a pooled connection, so saturation
appears as pool wait time. Capacity planning must size `instances × MaxConns`
against PostgreSQL connection limits and measure sustained authentication
throughput; that load test has not been run.

No authorization result caching was added. Replacing the authoritative checks
with an application cache would weaken revocation and was deliberately avoided.
